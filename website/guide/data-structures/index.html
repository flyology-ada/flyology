Store structures in caller-owned regions.

Initialize byte-oriented structures in a caller-owned region, optionally manage payload growth with a relocatable arena, attach process-local views at each virtual address, and use the synchronization model stated by each leaf.

These packages do not create mappings or provide IPC discovery. The application owns the backing bytes, mapping lifetime, descriptor exchange, permissions, flushing policy, and process-lifecycle policy.

STORAGE 01

Keep native addresses out of stored bytes.

A stored Flyology data structure contains fixed-width offsets, slot indices, generations, counters, hashes, state fields, and byte payloads. It contains no System.Address or Ada access value. A process-local leaf view, such as Vectors.View, may cache the native base and validated field addresses, but those values are not written to the region.

This separation allows the same physical bytes to be mapped at different virtual addresses. Each participant attaches a Regions.View to its own base and then attaches the leaf view at the same stored offset. Leaf operations resolve stored relationships through that local view.

Stored metadata
Every leaf records a 64-bit magic, layout version, schema, extent, configuration, lifecycle state, and initialization epoch.
Attachment
The expected identity and geometry must match. Null, truncated, misaligned, overflowing, incomplete, stale, or corrupt layouts fail before payload access.
Payload types
Public containers store explicit byte representations. An arbitrary Ada private type may contain hidden access values or compiler metadata and is not accepted as a persistable element.
Allocation
Bounded leaves keep fixed capacity. Dynamic leaves can replace payload allocations inside a fixed managed arena, but no leaf grows or remaps the backing region.
!

Relocatable does not mean cross-format serialization. Current layouts use host byte order and are tested on Flyology's 64-bit Darwin and Linux targets. Magic and schema checks do not establish cross-endian portability.

STORAGE 02

Choose the leaf by ownership and access pattern.

Byte_Strings.View
A bounded variable-length byte sequence. Ordinary operations share one persisted guard.
Vectors.View
A bounded sequence of fixed-size byte elements. Indexing is one-based at the public API.
Hash_Maps.View
Fixed-size byte keys and values in a bounded open-addressed table. Capacity is a power of two.
Arenas.View
A fixed managed extent with variable-size buddy allocations identified by generations rather than addresses.
Dynamic.Byte_Strings.View
A byte sequence whose payload capacity grows through an arena allocation.
Dynamic.Vectors.View
A fixed-element byte vector whose payload capacity grows through an arena allocation.
Dynamic.Hash_Maps.View
An open-addressed byte map that allocates and rehashes larger tables inside an arena.
Slab_Pools.View
Fixed-size slots returned as generation-stamped handles. Per-slot state separates unrelated accesses and detects stale handles.
Rings.SPSC.View
A bounded fixed-element queue with exactly one producer and one consumer.
Rings.MPMC.View
A bounded fixed-element queue with multiple producers and consumers, per-slot sequences, and bounded claim campaigns.
Envelopes.View
An optional application signature and contract version around one nested leaf. The nested leaf still validates its own identity and geometry.

Regions.View supplies a checked process-local backing view, while Handles.Handle is the fixed-width slot-and-generation representation used by structures such as slabs. Neither package owns storage.

STORAGE 03

Use an arena when payload capacity must grow.

Arenas.View manages a fixed region extent with a persisted buddy tree. Each successful allocation returns an Arenas.Allocation_Handle containing a tree-node index, arena initialization epoch, and nonzero allocation generation. The handle remains the stored relationship; the arena derives a checked process-local address only inside an operation.

The managed capacity and minimum block size are powers of two. Allocation rounds a request to the smallest fitting buddy block and reports allocation, exhaustion, or immediate metadata contention. Releasing a handle coalesces free buddies and makes every copy of that generation stale. Payload read, write, and copy do not acquire the metadata guard, so the handle owner must exclude release while payload access or a nested allocation-region view is active.

The dynamic leaves keep a fixed 128-byte header at their original region offset and move only the payload allocation. Growth allocates and initializes a replacement before publishing its handle. A deferred old handle remains recorded until reclamation succeeds, so arena contention cannot make a published allocation unreachable. Dynamic.Growth_Result separates completion, arena exhaustion, and arena contention.

Create_Or_Attach and Attach compare every immutable creation parameter. For an arena this includes managed capacity, minimum block size, and the caller-selected instance identifier. For a dynamic leaf it includes initial capacity, element or key/value sizes, and the arena instance plus initialization incarnation. A ready object with different parameters fails attachment; it is not reinitialized or adapted.

!

Growable is not an unbounded resource claim. Dynamic structures grow until allocation geometry or the fixed arena is exhausted. The arena does not extend a mapping, compact live blocks, or recover ownership after process death. Termination after allocation but before handle publication requires an external allocation journal or exclusive whole-arena reinitialization.

STORAGE 04

Initialize a structure in an attached region.

The application first obtains contiguous bytes, then attaches a region view. The example uses a local aligned arena; the same leaf calls apply to anonymous, file-backed, persistent, or shared mappings.

Required_Storage computes the complete extent for a chosen capacity and element size. Reserve that extent at a nonzero leaf-aligned Region_Offset; offset zero is the null sentinel. Initialization requires exclusive ownership of the target extent through final ready-state publication.

When an allocation protocol supplies an extent known to have an exact zero lifecycle but several participants may discover it, call Vectors.Create_Or_Attach, or the corresponding operation on another leaf. Its Open_Result is Initialized_New for the caller that atomically claims initialization, Attached_Existing for a caller that validates the completed compatible object, or Initialization_In_Progress with a detached view when another caller has not published yet. The operation does not wait. Concurrent calls are permitted while the allocation protocol still guarantees virgin bytes; once a ready object may exist, use the leaf's ordinary attachment-quiescence rule.

!

Creation is not recovery. Use Create_Or_Attach only when an outer allocation protocol establishes that zero means virgin storage. If corruption zeros the lifecycle word of an older object, the core layout cannot distinguish it from a new extent. Explicit Initialize remains the destructive recovery operation under exclusive authority.

Destroy invalidates a stored object when the leaf's quiescence preconditions hold. Detach only clears process-local state and leaves the stored bytes unchanged.

STORAGE 05

Attach independently at every mapping address.

Mapping creation remains outside these packages. After the application maps the same backing object again, attach another region using that mapping's base and attach the leaf with the expected configuration.

Reinitialization advances a nonwrapping initialization epoch. Every view attached to the earlier epoch becomes stale and fails before using cached geometry or native addresses. Detach those views and attach again. After the final epoch value, retire the extent rather than wrapping it.

Before unmapping a range, detach every leaf view derived from it and then detach the region view. A leaf view does not retain or extend the mapping's lifetime.

STORAGE 06

Add an application-level version when needed.

Every leaf already validates its own Layout_Identity. An application that assigns additional meaning to the payload can instantiate Envelopes with the leaf's exported Identity, a stable nonzero signature, and an application-controlled contract version.

Envelope initialization first marks the nested lifecycle incomplete, publishes the envelope, and leaves nested initialization to the caller. If execution stops between those steps, leaf attachment rejects the incomplete nested object. The 64-bit signature reduces accidental contract confusion; it is not authentication or an integrity checksum.

STORAGE 07

Use the synchronization model stated by the leaf.

Relocation and concurrency are separate properties. Region attachment and backing lifetime are never internally synchronized. Leaf initialization, attachment, detachment, destruction, and reinitialization require the documented quiescence even when ordinary operations are internally coordinated.

Guarded containers
Byte strings, vectors, and hash maps serialize ordinary operations across separate attached views. Immediate operations make one claim and raise Busy_Error on contention.
Timed guarded access
Timed overloads retry through one Wait_Timeout and yield between contended observations. A zero timeout permits one immediate attempt.
Slab pool
Allocation reports an Allocation_Result after a bounded capacity scan; payload access and reclamation claim one slot. Timed overloads retry transient claim contention, but true exhaustion still returns Exhausted.
SPSC ring
Exactly one producer calls push operations and exactly one consumer calls pop operations. Producer and consumer may use different mappings.
MPMC ring
Multiple producers and consumers use process-capable atomics and per-slot sequences. Try operations retain bounded failure outcomes.

A timed operation starts its monotonic deadline at the first failed claim. It uses delay 0.0 between attempts: a lightweight caller yields its fiber, while a native caller yields its pthread. It does not allocate a persisted wake object or issue a blocking wait syscall on an event-loop pthread.

!

Do not race one local view's attachment state. Internal synchronization coordinates ordinary operations through separate attached views. The application must exclude Attach, Detach, mapping release, and similar local-state changes from every concurrent use of that same view object.

STORAGE 08

Separate corruption detection from owner-death policy.

Layouts fail closed on corrupt identity, geometry, state, counters, and handles, but the core packages do not determine whether another task or process has terminated. Poison operations therefore require an independently authorized caller that has already established owner death and the leaf's required quiescence.

Guard abandoned
A dead owner can leave a byte string, vector, or hash map locked. Timed access eventually raises Timeout_Error; it does not unlock the object. A supervisor may poison only after establishing whole-object quiescence.
Slab operation abandoned
A transitional state affects one slot. Authorized recovery marks that slot poisoned and explicitly recycles it with a new generation. A published live allocation whose returned handle was lost requires an external ownership journal or whole-pool reinitialization.
MPMC claim abandoned
Termination after a position claim and before sequence publication can stop later progress. Recovery requires ring-wide quiescence, poisoning, and exclusive reinitialization.
Mutation exception
If a guarded mutation may have changed stored bytes before raising, the leaf publishes poison rather than returning the object to ready state.

Exclusive Initialize is the unconditional whole-object recovery path. It invalidates earlier views through the lifecycle epoch; every participant must attach again.

STORAGE 09

Review the complete lifetime sequence.

  1. Choose capacity and element geometry, then compute Required_Storage.
  2. Allocate or map a contiguous region with the required extent and alignment.
  3. Attach one Regions.View per local mapping.
  4. Initialize under exclusive ownership, or attach with the exact expected identity and geometry.
  5. Use only the synchronization model documented by that leaf.
  6. Before reinitialization, destruction, mapping replacement, or recovery, establish the required quiescence.
  7. Detach every leaf view, then detach the region view, before unmapping or releasing the backing bytes.

A failed leaf attachment leaves its output view detached. Is_Attached reports retained local mapping information; it does not promise that a later reinitialization has not made the cached epoch stale.

STORAGE 10

Keep the core boundary explicit.

  • The packages do not open, name, map, resize, flush, or close backing storage.
  • They provide no peer discovery, descriptor transfer, access-control policy, wake channel, or automatic process-death recovery.
  • Persisted payloads are bytes. Applications define encoding, validation, and schema migration for those bytes.
  • Timed operations cooperatively retry; they do not provide a pollable completion descriptor.
  • Crash consistency of an application transaction spanning several structures requires an application protocol.
  • The current implementation is experimental and has not been qualified as a general persistent database or crash-recovery system.
  • Use the generated API reference for exact parameter, exception, and synchronization contracts.
