STEP 01

Start with an exact toolchain.

Flyology is an Alire crate and requires Alire 2.1 or newer. The crate accepts GNAT 13 through 16 as a dependency range, but runtime preparation supports only the host and release pairs listed below.

macOS / AArch64
13.2.2, 14.1.3, 14.2.1, and 16.1.0
Linux / AArch64
13.2.2, 14.1.3, 14.2.1, 15.1.2, 15.3.1, and 16.1.0
Linux / x86-64
13.2.2, 14.1.3, 14.2.1, 15.1.2, 15.3.1, and 16.1.0
!

The dependency range is not the support matrix. Runtime preparation checks the exact active compiler and fails rather than guessing a nearby patch family.

STEP 02

Add Flyology to an Alire application.

Flyology is temporarily published through a separate organization index. Keep the community index enabled for compiler and third-party dependencies, add the Flyology index ahead of it, and add the crate normally.

i

The Flyology index is a development channel, not a community-index release. Remove it with alr index --del flyology when Flyology is available from the community index.

STEP 03

Build with a version-matched runtime.

The first build runs Flyology's Alire post-fetch action. It copies the active compiler's installed runtime sources into dependency build output, applies the exact patch family, builds the RTS, and exports a GPR configuration that selects it. The application links against this prepared RTS rather than the stock tasking runtime.

The default is native. This is the compatibility configuration: undesignated tasks stay on stock OS-thread execution, and no event machinery starts until a lightweight task is activated.

i

Preparation settings are compiled into the RTS. They are not read dynamically by the application at startup; after changing one, rerun the preparation command and alr build.

FLYOLOGY_DEFAULT
Selects native or lightweight for tasks that do not carry an explicit designation.
FLYOLOGY_LOOP_POOL_SIZE
Selects 1 .. 128 shared groups for automatic round-robin placement. Groups and their OS threads still start lazily.
Loop placement
FLYOLOGY_LOOP_PLACEMENT and FLYOLOGY_LOOP_PLACEMENT_MAP request Linux strict logical-CPU binding or a supported Darwin advisory tag. This places loop threads; it does not change task-to-group assignment.
STEP 04

Designate one ordinary Ada task.

Use GNAT Task_Info to select the execution model at task creation. The obsolete-feature warning is deliberate; Flyology projects retain other warnings while using -gnatwJ for this mechanism.

Explicit Flyology.Native_Task and Flyology.Lightweight_Task values override the prepared project default. Flyology.Project_Default requests that default explicitly, which is useful on discriminated task types.

STEP 05

Size each task stack deliberately.

Ada's Storage_Size is the stack-size control for both native and lightweight tasks. Put the pragma in the task or task-type declaration, use a named constant so the choice is reviewable, and size for the deepest real call path: local objects, recursion, exception propagation, and foreign calls all consume stack.

The requested value is not the task's complete memory footprint or necessarily the final usable mapping size. The tasking runtime adds its conservative alternate-signal-stack allowance, and Flyology rounds a lightweight stack to the host page size. Lightweight stacks are placed in guarded arenas; each slot carries at least 64 KiB of inaccessible guard address space. Native tasks instead retain the host pthread implementation and its platform minimums.

!

Do not find the minimum by waiting for a guard fault. A guard improves failure behavior but cannot prove every stack path safe. Exercise worst-case nesting and exception paths, include margin, and repeat the test on every supported compiler and host.

Flyology.Observability.Stack_Pool reports the effective lightweight result. Live_Usable_Bytes is the aggregate usable size after runtime adjustment and page rounding; Reserved_Bytes is the exact virtual address space held by live arenas, including guards. Reserved address space is not resident memory, so measure process RSS separately.

If every live lightweight task in a sample uses the same declaration, divide Live_Usable_Bytes by Live_Stacks to obtain its effective usable size. With mixed task sizes that quotient is only an average. The current structured-server generic owns its handler task type and uses the compiler/runtime default stack size; Storage_Size applies directly to task types declared by the application.

STEP 06

Manage memory by lifetime and reclaimability.

Flyology keeps three questions separate: how much virtual address space a task stack reserves, whether a sleeping lightweight task permits best-effort reclamation of resident stack pages, and when task-private heap objects can be finalized and released together. None of these controls is a process memory limit.

Stack capacity
Use Ada Storage_Size and the stack-pool snapshot described above. This controls usable stack sizing; it does not request paging.
Dormant stack residency
Use Flyology.Dormancy for a lightweight task that will wait only on a sufficiently distant timer and can tolerate a slower wake.
Task-private object lifetime
Use Flyology.Memory_Regions when a group of allocations belongs to one task phase and can be finalized and released together.
Shared or transferred data
Keep it in an explicitly shared owner or bounded pool. A task-owned region is not a shared allocator, and references into it must not outlive the region.

Opt a timer sleeper into stack reclamation

Prompt is the default dormancy policy. Reclaimable asks a supporting Linux kernel to mark applicable stack pages cold; Page_Out asks it to reclaim applicable pages through the configured swap path. Both policies apply only after a lightweight task has switched safely to its scheduler stack and is waiting solely on a timer whose remaining delay is at least Minimum_Wait.

Descriptor waits are excluded because scheduler links may remain on the suspended stack. File waits are excluded because the kernel may still own a stack-backed buffer. Native tasks accept only Prompt. On unsupported hosts the capability queries report false and no page advice is attempted.

!

Page advice is a latency tradeoff, not an eviction guarantee. The kernel may ignore individual pages, and a task waking after accepted advice may incur page faults. Prompt also does not lock a stack into physical memory.

Use Cold_Advice_Supported and Pageout_Advice_Supported before presenting a host capability. Group snapshots distinguish eligible timer waits, currently advised stacks and bytes, advice attempts, accepted calls, and failures.

Release task-private allocations as one region

Flyology.Memory_Regions.Task_Pool is owned by the native or lightweight task that declares it. Each region grows in backing chunks as named-subpool allocators request storage. Explicit release first finalizes controlled objects and then returns every backing chunk; finalizing the pool releases any regions that remain live.

A pool object declared in a task body is finalized when the task ends, so its remaining live regions are released automatically. Call Release when an earlier lifetime boundary matters. A dynamically allocated pool is not reclaimed merely because its owning task ends; the application must arrange for the pool to be finalized and deallocated.

Every allocator for an access type associated with the pool must name a region; an unnamed allocator raises Program_Error. Calls from another task raise Ownership_Error. Statistics reports live regions, consumed storage including allocator overhead, and reserved chunk capacity.

Understand the region cost model

The efficiency comes from grouping objects that share a lifetime. The pool replaces repeated general-heap allocation and reclamation with allocation from larger chunks and one collective cleanup boundary.

Task pool
Stores fixed ownership and accounting state plus the Ada subpool controller. Flyology adds no per-pool mutex because only the owning task may use it; the tasking runtime briefly takes its lock when a region is attached to or detached from the controller's subpool list.
Region creation
Allocates one Flyology region descriptor and one runtime registration node while attaching it to the pool. The first backing chunk is allocated lazily by the first object.
Common allocation
Checks task ownership, aligns an address, advances the current chunk offset, and updates counters. It takes no region lock and does not call the underlying heap while that chunk has room.
Chunk growth
Allocates and links one new chunk when the current chunk is full. The default payload capacity is 64 KiB; a larger object receives enough capacity for its size and alignment.
Bulk cleanup
Finalizes controlled objects, detaches and frees the runtime registration node, frees each backing chunk, and frees the region descriptor. Explicit Release does this for one region; task-end pool finalization does it for every region still live.

For N object allocations spread across R regions and K chunks, Flyology and the supported runtime make roughly 2R + K underlying management allocations: one descriptor and one registration node per region, plus the chunks. Most of the N object allocations are bump operations inside an existing chunk. Reclamation performs the corresponding management frees, although controlled objects still require individual finalization. This amortization is useful when R + K is much smaller than N.

Reclamation is synchronous rather than background work. Ending a lightweight task with many chunks or expensive finalizers can occupy its event-loop pthread until cleanup finishes. The allocator checks only the current chunk, so unused tails in older chunks remain reserved until release. Reserved_Storage counts chunk payload capacity, not region descriptors, chunk headers, or underlying allocator metadata. Use smaller phase regions and explicit release boundaries when cleanup timing or chunk slack matters.

The current implementation has no region quota, retained-chunk cache, trimming operation, or automatic connection to dormant-stack advice. It does not redirect ordinary Ada allocation. Set application admission limits around potentially large phases, inspect region statistics before release, and treat every access value into a released region as invalid.

i

Use regions for parsing trees, temporary metadata, and other task-private object graphs. Do not use them as backing storage for a buffer or object whose ownership moves to another task.

STEP 07

Choose an execution group.

A lightweight task without a specific Ada CPU is placed into the configured shared pool by deterministic round robin. A CPU aspect selects an exact Flyology execution group instead.

Tasks in one group share a stable loop thread and schedule cooperatively. Separate groups use separate OS threads and may execute in parallel. Shared group identifiers are 0 .. 127; dedicated group identifiers are 128 .. 255.

Migration is an explicit safe point

A lightweight task can move to another group without changing Ada task identity, stack, locals, or exception state. Use a scoped thread pin while holding thread-affine foreign state, and use a dedicated group when exclusive OS-thread ownership is also required.

STEP 08

Use synchronous I/O calls.

Flyology I/O packages expose normal procedure and function calls from either lane. If a lightweight call would block, only that task waits; the loop thread remains available. A native call may block only its OS thread.

For relative waits, monotonic deadlines, adjustable wall-clock targets, and backward-clock detection, continue with the timers guide.

Use the ownership-aware connection packages when descriptor lifetime, cancellation, and close races matter. Raw descriptor waits deliberately leave lifetime serialization to the caller.

STEP 09

Set resource budgets before load testing.

Flyology does not turn one number into a complete capacity plan. Bound the resources the application owns, set latency limits at operation boundaries, and then measure them together under representative peak load.

Concurrency
Use a structured server or Connections.Server capacity to cap simultaneously owned connections. A structured server creates exactly Capacity handler tasks for the duration of Serve, including while idle.
Stack memory
For homogeneous lightweight tasks, plan usable stack bytes as peak live tasks multiplied by the observed effective bytes per task. Read Reserved_Bytes for guarded virtual address space and measure RSS for resident memory.
Task-owned regions
Region storage currently grows on demand without a built-in quota. Bound the number and size of admitted phases, sample Statistics, and call Release at the earliest valid lifetime boundary.
Dormant stacks
Choose Minimum_Wait from tolerated wake latency and representative host measurements. Accepted cold or page-out advice does not reduce the configured stack capacity.
Parallelism
FLYOLOGY_LOOP_POOL_SIZE bounds automatic shared groups, not task count. Start near the CPU parallelism the workload can use and compare measurements; each created group adds an OS thread plus poller, scheduler, and kernel-queue resources.
Latency
Use finite I/O deadlines, a bounded shutdown drain, and checkpoints in CPU loops. These are separate limits: cancellation is not a timeout, and a fairness quantum is not a hard execution deadline.

Bound admission, not just the listen backlog

The structured-server capacity is both the maximum active handlers and an eager task-resource budget. Excess work remains in the kernel listen backlog instead of becoming an unbounded user-space task or connection queue.

Give an operation one meaningful deadline

Receive_Exactly and Send_All apply one timeout across the whole multi-step operation rather than restarting it for every partial transfer. DNS resolution similarly applies its overall timeout across family queries, retry rounds, and transport fallback. Prefer finite deadlines at service boundaries; reserve Infinite for scopes whose shutdown and cancellation path is otherwise explicit.

Add checkpoints to bounded units of CPU work

A CPU-bound lightweight task can monopolize its group until it reaches a runtime suspension, executes delay 0.0, or calls a fairness checkpoint. Priorities choose among ready fibers within a group, but they do not preempt arbitrary lightweight instructions. A new Yield_Budget defaults to a 2 ms quantum; configure it when the service needs a different cooperative slice.

Choose a quantum below the same-group scheduling delay the application can tolerate, then measure it. The value is elapsed wall-clock time between eligible yields, not reserved CPU time. Put Checkpoint after a bounded unit of work: if Process_One_Item itself can run for 50 ms, a 250 µs quantum cannot take effect until that call returns. Very small quanta also increase clock reads and scheduler transfers.

!

An arbitrary blocking foreign call can stop every lightweight task in its group. Put unpredictable blocking work on a native task or migrate to a dedicated group first.

STEP 10

Observe, compare, and adjust one knob.

Take snapshots at idle, representative load, and recovery. Group snapshots are coherent but briefly hold scheduler locks and cost O(group members), so sample periodically rather than per request. Lifetime counters wrap and do not reset; compare two samples instead of treating one cumulative value as a rate.

Healthy waiting
A high Waiting count accompanied by timer, descriptor, interrupt, or file waits normally means concurrency is parked in the intended kernel-backed path.
Runnable pressure
A persistently high Ready count means runnable work is sharing the group. Compare dispatch progress, CPU use, checkpoint placement, and the result of adding a group.
Possible stall
Ready or running work without changes in dispatch or polling counters is a loop-lag signal. Stall_Watchdogs can sample this condition from a native monitor task; it diagnoses but does not preempt.
File pressure
Pending_File_Submissions shows file operations waiting behind the bounded kernel completion queue. It is backpressure, not a hidden worker-thread queue.
Stack pressure
Track live stacks, effective usable bytes, guarded virtual reservation, process RSS, and task-creation failures together. None of those values alone is a complete memory limit.
Dormant stack effect
Compare candidate bytes, currently advised bytes, cumulative accepted and failed advice, process RSS, and timer wake lateness. Advice counters do not prove that pages were evicted.
Region growth
Read consumed and reserved region storage before release. Reserved minus consumed shows current chunk slack, not leaked memory.

The density run compares lightweight and native tasks with the same requested stack size and reports RSS, virtual address space, thread count, and lightweight stack-pool counters. The pool run compares one event loop with a configured pool under repeated readiness waves. The dormant-stack run compares Prompt, Reclaimable, and Page_Out in separate processes while verifying every touched stack payload after wake. Treat each result as a measurement of that host and workload, not a universal sizing constant.

STEP 11

Run the checks for your changes.

The repository scripts are authoritative for behavioral tests, proofs, documentation, stress campaigns, and showcases.

  • test.sh runs both project defaults, runtime-preparation validation, and an external consumer.
  • stress.sh runs bounded deterministic concurrency and fault campaigns.
  • prove.sh runs the SPARK policy proof suite.
  • docs.sh generates the public GNATdoc reference with undocumented-entity warnings enabled.
STEP 12

Know when to stay native.

Flyology Runtime is experimental. Keep a task native when its correctness depends on kernel real-time scheduling, forced preemption, native CPU affinity, unpredictable foreign blocking, or a host and compiler combination outside the verified patch matrix.

Use lightweight
High I/O concurrency with cooperative work, explicit task-aware waits, and ordinary Ada task semantics.
Use native
Blocking foreign libraries, kernel scheduling policies, independent OS-thread execution, or unmodified compatibility behavior.
Use dedicated
A lightweight continuation must temporarily own a stable loop thread exclusively.
