Restart a service without escaping its Ada scope.

A supervisor owns fresh task generations, waits for explicit readiness, coordinates dependent recovery, and returns only after structured join. Recovery is typed and bounded, but it cannot make shared memory safe or force an uncooperative task to terminate.

WHY SUPERVISION

One logical service, successive task objects.

A long-running task can return unexpectedly, raise an exception, fail during activation, or never become usable. A supervisor keeps the service identity stable while owning each concrete Ada task object as a separate generation.

  1. Construct generation 1 under the supervisor's Ada master.
  2. Wait until the task reports that its resources and application state are ready.
  3. If it fails, request stop where necessary and wait for task-body cleanup, dependent-task joins, and finalization.
  4. Consult the bounded restart policy. If recovery is admitted, wait for backoff and construct generation 2 from fresh resources.
  5. On shutdown or exhausted policy, join everything the supervisor owns before Run returns.

The supervisor does not resurrect a terminated task. It decides whether to construct a replacement and keeps that replacement unpublished until it is ready. This is useful for restart-safe service loops, listeners, polling agents, caches, connection-like dynamic children, and subsystems with declared startup dependencies. It is a poor fit when work cannot be repeated safely, a child borrows shorter-lived state, or partial shared-memory and external effects cannot be reconciled.

Erlang/OTP made supervision trees a durable way to separate service work from recovery policy. Flyology keeps that core idea while expressing it through application-defined Ada task types, masters, bounded policy, and explicit resource reacquisition. Ada tasks share memory and external resources, so supervision cannot supply process isolation or guaranteed forced termination.

i

Lightweight and native tasks. Every Flyology task remains an ordinary Ada task, but it executes in one of two ways. A lightweight task is scheduled cooperatively with other lightweight tasks on an event-loop pthread in a Flyology execution group. A native task runs on its own pthread using the ordinary native task path. Both retain Ada activation, masters, rendezvous, protected objects, exceptions, finalization, abort deferral, and task identity.

The task declaration chooses the actual execution model: pragma Task_Info (Flyology.Lightweight_Task) selects a lightweight task, Flyology.Native_Task selects a native task explicitly, and an undesignated task is native by default. For a lightweight task, its CPU aspect selects the Flyology execution group; for a native task, CPU retains its ordinary affinity meaning. The supervision field Task_Model => Flyology.Lightweight_Task records the same expected model for policy validation and observation; it does not designate, move, or schedule the task. The task declaration remains authoritative.

FIRST EXAMPLE

Supervise one restartable service.

This is the complete supervision wiring for one polling service. Only the application-defined context, resource, acquisition, and sampling details are omitted. The application declares the actual task type, its entry, execution model, and execution group. Flyology owns each constructed task object through termination and join, and the task-result facility records how it exited.

i

What the generation operations do. Each formal subprogram is statically tied to Metrics_Task. Create chooses its discriminants and constructs the exact task object by limited build-in-place return. Task_Identity supplies the identity used to await its task-owned result, and Abort_Task supplies the optional last-resort stop request. Those three operations use the generic's is <> defaults, so compatible directly visible declarations are inferred by name. Initialize stays explicit: omitting it selects the useful null default rather than an inferred startup rendezvous. Together the operations let the generic own a task generation without defining the task's entries, body, or service API.

i

Exit reporting is automatic. After task-body cleanup and dependent-task joining, Flyology.Task_Results publishes normal completion, abnormal completion, or an escaping exception with a bounded fully qualified name and message. Task_Generations maps that immutable result into supervision state while the task object is still alive. Explicit Report_* calls are needed only when application code catches and suppresses an outcome but deliberately wants supervision to classify it differently.

The inner block makes Resources finalize while an exception unwinds or before a normal return; GNARL publishes the terminal result afterward. The policy is explicit: an unexpected exception from Sample is a failure, On_Failure admits replacement, and Isolate_Child limits recovery to this child. The task type itself selects lightweight group 2; the policy declares the same placement for bounded observation but cannot inspect or override the task type's actual aspects. The controller joins the failed task, applies Limits, and invokes Run_Generation for a new Metrics_Task. Run synchronously owns the tree; another task may call Request_Shutdown, and Run returns only after every terminable generation and manager has joined.

MODEL

A restart is a replacement, never resurrection.

A terminated Ada task does not start again. Flyology constructs a new object of the application task type, assigns the next generation, and withholds publication until that generation reports readiness. The old generation must finish task-body cleanup and join before replacement construction begins.

The synchronous Run call is the ownership boundary. Manager tasks, generation controls, copied requests, event storage, and child task objects cannot outlive that call's Ada master.

TOPOLOGY

Choose by topology, not by expected child count.

Supervision.Static
Use an enumeration for a heterogeneous tree. Each member may have a different task type, execution model, restart rule, dependency set, and named recovery cohort. Storage includes a fixed dependency matrix.
Supervision.Families
Use fixed slots for many homogeneous children with one typed request and one common policy. Storage is linear in Maximum_Children; no dense dependency matrix is allocated.
Nested node
Run either controller inside a supervised generation with Run_Nested. A failure carries the same incident, attempt, and absolute recovery deadline into the parent.

Child_Id is a nonzero 64-bit logical identity. Each generic instantiation declares its own fixed capacity, so memory use is visible in the type and configuration.

IDENTITY

Use the logical id to observe and the generation to act.

Child_Id
Stable service or slot identity across replacement. Use it for dashboards and logical lookup.
Generation
Nonzero 64-bit construction identity. It advances on restart and on dynamic slot reuse, never wraps, and fails closed if its successor space is exhausted.
Child_Handle
The exact controller, logical id, and generation. A handle from another supervisor is stale even when the displayed id and generation match. A default-constructed handle has invalid controller authority. Stop, manual restart, and health reports require an issued exact handle.
Ada.Task_Identification.Task_Id
Copied diagnostic identity of the actual task object. It is never used to address a replacement.
  1. Configured
  2. Starting
  3. Ready
  4. Running
  5. Stopping
  6. Terminated
  7. Backing off
  8. Restarting
  9. Starting
  10. Joined

Ready records the application handshake. A controller may publish it atomically as Starting -> Running; activation alone is never enough. Joined means the task can no longer publish, its task-body finalization and dependent-task joins completed, and supervisor-owned generation state is reclaimable. Stuck is a termination classification, not a claim that a live task was killed.

MONITORING

Observe one exact task or one exact generation.

Observation is passive. It tells a caller how one task or generation ended; it does not cancel, abort, restart, or otherwise signal the target. Flyology keeps concrete Ada task identity separate from the logical identity that survives a restart.

A task-result monitor names the exact Ada.Task_Identification.Task_Id supplied to Attach. It never follows a later task. Multiple monitors may retain the same fixed sidecar, but each limited monitor must outlive every task that calls Observe or Wait on it.

Monitor_Capacity on each static or family generic bounds concurrent generation waits. A timed-out, aborted, or unwinding waiter releases its registration. Slot tokens prevent late cleanup from canceling a newer waiter that reused the same bounded slot.

i

Failure coupling is structured policy. A task scope can cancel sibling operations after one fails. A supervisor can isolate a child, restart a named cohort, restart declared dependents, or escalate the same incident to its parent. Flyology does not add a symmetric raw task link: in shared-memory Ada, a link cannot infer resource ownership, restart safety, or which sibling state remains valid.

There is no general wait-any monitor set in this slice. Exact task waits, exact generation waits, and bounded controller event rings cover the current consumers without adding hidden publication fan-out or another lifetime owner.

PUBLICATION

Publish a typed lease, not an access-to-task value.

A task entry may remain part of the application task type, but a long-lived client must not retain an access value to a task object that will be replaced. Service_Slots instead publishes a fixed scalar lease for one typed service and one exact controller-qualified generation. The application endpoint remains in a protected object or bounded channel owned by the surrounding context.

Current is useful for observation, but check-then-use is not authority. The protected endpoint operation must validate the lease while it performs the mutation. When the old task finalizes, its controlled publication becomes unavailable. A replacement constructs fresh resources, reports readiness, and publishes a different generation; every copied old lease remains stale.

OPERATIONS

Manual restart and health failure use the same recovery path.

Operational commands never address a logical service alone. Capture Latest, perform the probe against that generation's endpoint, then submit the same exact handle. If replacement won the race, the controller raises Stale_Handle and leaves the new task untouched.

A manual restart, external failed probe, internal failed probe, and automatic exception all pass through configured impact, reverse-order stop, join, backoff, fresh construction, readiness, and bounded event recording. A command is rejected if stop, supervisor shutdown, terminal escalation, or another intervention reached the controller first, even if the old Ada task has not completed yet. Manual restart is not an unmetered maintenance shortcut. Health checks should report actionable service usability, not transient load that ordinary backpressure already represents.

STATIC

Describe heterogeneous services with ordinary Ada types.

The generic takes typed functions for identity, policy, dependencies, and cohort membership. An exhaustive dispatcher selects the task-generation package for each enumeration value. Every service may use a different application task type; no address-valued payload or universal callback context is needed.

Request_Shutdown is sticky. A request made before Run, or while its configuration callbacks are still being validated, prevents manager and child activation instead of being overwritten by configuration.

Run_Generation normally calls an instance of Flyology.Supervision.Task_Generations. The first example shows the one-child form; a larger dispatcher uses one package per task type. Inside each task body, acquire and validate the listener, descriptor, buffer, dedicated execution group, or other generation-owned resource, then call Mark_Ready. A failed bind never becomes visible as a running service.

i

Task entries remain local to the generation. Initialize may use startup entries, and tasks owned inside the generation may use normal lexical references. Do not publish a naked access-to-task value. For a long-lived client API, route typed commands through a protected object or bounded channel in the application context and include the Child_Handle returned by Handle (Control); the receiver rejects a stale generation.

RECOVERY

Recover an explicit set in dependency order.

A static node validates an acyclic dependency graph before activating a task. It starts the lowest-id ready child first and stops in reverse topological order. A failure selects one of four impacts.

Isolate_Child
Stop, join, and replace only the failed child.
Restart_Cohort
Use the typed Cohort_Member relation to restart an explicitly named set.
Restart_Dependents
Restart the failed prerequisite and every transitive declared user.
Escalate
Perform no local reconstruction. Stop the node and return the causal incident to its owner.

For Database -> Cache -> API, a database failure with Restart_Dependents stops API, then Cache, joins Database, waits once, and starts Database, Cache, then API. Each replacement must report readiness before its dependent starts. An unrelated Telemetry child continues.

!

Configuration rejects an affected child without Restart_Safe and a recovery set that would leave a running dependent attached to a replaced prerequisite. This flag is an application acknowledgement, not a proof of idempotence or shared-state safety.

FAMILIES

Scale homogeneous children with fixed linear storage.

A family uses one application task type and one typed request type for every slot. Input_Task_Generations keeps a stable immutable request copy beside the task object through join. The family reserves a slot under its protected state, copies the request outside that lock, then commits admission. Shutdown waits for every outstanding reservation to commit or roll back; a commit that loses the race with shutdown is rejected and rolled back. Reusing a free slot advances its generation and starts fresh recovery accounting. The family allocates one persistent manager lazily for each slot that is ever used. Managers are bounded by Maximum_Children, are reused with their slots, and finish at the family scope's join boundary. Their task-object storage is reclaimed only after termination is observable.

Current (Family, Handle) is exact and raises Stale_Handle after replacement or reuse. Current (Family, Child_Id) is an observational lookup of the latest occupied generation and does not grant authority to mutate it. Capacity exhaustion raises Constraint_Error before admission.

A family policy may isolate one slot or escalate its incident. All slots share the task type, policy, and configured task model or group; use separate family instances when those differ. Named cohorts and dependency closure describe heterogeneous topology, so place the family as a child of a static node when its recovery must coordinate with a database, listener, sibling family, or other service. The containing static node may restart that family child as part of a cohort or dependent closure. The family never infers relationships among independent requests.

BUDGETS

Count one recovery cascade once.

The first recoverable failure creates an Incident_Id, attempt 1, and an absolute monotonic deadline. Cohort members and nested nodes receive that same context. A node records a given incident and attempt at most once, so crossing a tree boundary does not silently multiply the retry allowance.

Burst and window
Reject another attempt after the fixed count within a monotonic window.
Total attempts
Bound all attempts in the incident even when windows roll over.
Backoff
Double the delay after each consecutive attempt and cap it at Maximum_Backoff.
Stability reset
After a replacement remains ready for the child and subtree intervals, close the inherited incident. A later failure starts at attempt 1 with a fresh absolute deadline; a nested escalation reported during the generation is retained.
Recovery deadline
Reject a delay that cannot finish before the inherited absolute deadline.

Static nodes apply both child and subtree limits. Dynamic families apply the common child policy to each slot and can be placed under a static node when a wider subtree budget is required. Exhaustion stops owned children, records Policy_Exhaustion, and returns Recovery_Exhausted with the same incident.

STOPPING

Deadlines classify progress; they do not force completion.

Stopping first publishes a fresh cooperative cancellation token. After Grace, policy may request Ada abort. After Abort_Observation, a still-live generation is classified Stuck. No replacement starts while that old generation or its task-owned finalization remains live.

  • A lightweight task can monopolize its cooperative execution group if it never suspends.
  • A native task can remain inside a foreign call that does not return.
  • Ada abort may be deferred in a protected action, rendezvous, finalization, or another abort-deferred region.
  • A synchronous supervisor cannot return while a dependent task remains live. A stuck child is observable, but the Ada master still waits.

Each new generation must reacquire sockets, descriptors, unique buffers, dedicated execution groups, thread pins, capacity permits, and provider sessions through its normal typed initialization path. Do not carry a borrowed token, callback access, resource handle, or pointer into the old task's locals across generations.

i

Supervisor managers and generation owners default to lightweight execution group 127. Keep supervised lightweight children off that group. Many supervisors can share this one control plane, so the design does not create one pthread per supervisor. Generation dispatch, Initialize, identity, and abort adapters must be bounded or suspend promptly; the service loop belongs in the application task's declared execution model and group.

ADAPTERS

Wrap an existing structured blocking service without changing it.

Supervision.Adapters accepts a fresh limited service constructor plus its blocking run, shutdown, and readiness operations. One dependent service-owner task executes the blocking call while the supervisor's generation runner observes readiness and forwards supervisor stop. The owner task is the concurrency boundary that leaves Worker_Pools.Run, IO.Structured_Servers.Serve, and application listener-loop APIs unchanged.

The generation result retains the service owner's actual Ada task identity. Normal return, the original escaping exception name and message, and abnormal completion keep their classifications instead of becoming an adapter wrapper exception. Service activation failure reaches the controller as Tasking_Error. The adapter does not assert that retrying jobs, requests, or accepts is safe. It only enforces a fresh one-shot service object, readiness ordering, cooperative stop forwarding, and structured join. The child still needs an explicit restart-safety review.

ROOT

Let the application scope own and consume the root result.

The canonical root context and supervisor live in the environment task's application scope, and the environment task calls synchronous Run directly. A dependent shutdown watcher translates process notification into Request_Shutdown; a low-level signal handler must not call the supervisor, format events, or run application callbacks.

A nested escalation carries one incident and attempt to its parent, so crossing a node does not multiply recovery consumption. The root has no parent budget. It returns one typed outcome after join; the application maps that outcome to shutdown, degraded operation, or process failure. The usual choice for exhausted or escalated recovery is a failing process exit so an external service manager may decide whether to create a fresh process. In-process reconstruction, when application semantics permit it, must use a fresh context, supervisor, resources, publications, and nested Ada scope rather than reusing the exhausted root.

EVENTS

Copy decisions out, then format them.

Each controller keeps a fixed snapshot per logical child and a fixed-capacity event ring. Protected actions append scalar and bounded copied data only. Logging, callback invocation, allocation, and finalizing user assignment stay outside the lock.

An event records sequence, monotonic time, logical id, generation, lifecycle transition, task model and group, termination kind, incident, and admitted backoff. If writers overwrite unread events, Dropped reports the exact sequence gap. The retained state is sufficient to reproduce ordering and restart admission without logging from GNARL's terminal publication path.

✓

Verification boundary. The fixed policy kernel is SPARK-proved for complete successful start plans, prerequisite precedence, exact isolate and cohort sets, dependent-recovery closure, restart accounting, backoff, incident, generation, and family-join decisions. Static and family controllers consume proved generation matching for generation-qualified publications and commands, and they apply the proved retained-event predicate before recording lifecycle, stop, and restart-admission edges. Family admission is derived from configured, shutdown, and terminal state; proved command gates reject default controller authority, intervention after stop or shutdown, and generation construction after those states. The exact-generation stop predicate accepts a queued child or a still-live managed child, never a terminated generation awaiting replacement. The deterministic lowest-id tie-break and exact minimal dependent set remain executable and model-tested. Task activation, readiness, protected state, cancelable waiting, stopping, finalization, and resource reclamation are covered by live semantic tests rather than claimed as SPARK-proved.

BOUNDARY

Keep the safety boundary visible.

  • Supervision does not isolate memory. Siblings may share protected and unprotected application state, file descriptors, external services, and foreign libraries.
  • Restart_Safe does not make partial external effects idempotent. Document reconciliation, ownership, and generation boundaries for each restartable child.
  • Readiness says the child chose to publish usability. It cannot prove the application's readiness check was complete.
  • Event storage, child slots, dependency matrices, managers, messages, and attempt accounting are bounded by declared types and generic capacities.
  • Flyology is experimental. Validate both lightweight and native tasks, startup rollback, cancellation, finalization, resource reacquisition, and stuck behavior for the exact host and compiler release.

A marker interface would not make this boundary stronger: an Ada task may still reach shared memory, foreign libraries, and external systems outside that type. The reviewable evidence is structural. Construct a fresh limited task or service object, keep owned resources in its finalized scope, publish only a controller-qualified ready lease, test that old and replacement ownership never overlap, and place reconciliation rules beside the policy that sets Restart_Safe => True.
